# Deal-Hunter Roadmap

> 这份文件是项目的长期记忆，取代 README 里的勾选清单。
> 每个 Milestone 都必须能实际验收；做完立刻回来更新，不要让它变成愿望清单。

## Vision

跑在自家服务器上的羊毛侦察兵：宽采集、狠去重、可解释评分，**一天一份日报**。
单二进制、零第三方依赖、无数据库、默认不对外网暴露。

## Current State

- 交付形态已从「发现即推的雷达」改为三类消息：每天一份日报、高分当天最多插队一条、限时事件开抢前提醒（M2/M3）。
- 采集、评分、官方链接校准、近似去重、投递后端（飞书卡片 + OpenClaw drop/relay + console）、只读面板均在位且有离线测试。
- 门禁是本机与办公室构建机上的脚本；**不使用 GitHub Actions**。
- 部署形态仍是一个 systemd 单元 + `/var/lib/deal-hunter` 状态目录（`deploy/install.sh`）。

## 已实测否决的方向（别再试第二遍）

- **「按标题长前缀折叠日报里的重复条目」**（2026-09-21 量过，**不能做**）：诱因是真的——
  `AgentCloak 推出免费浏览器扩展…` 两条同功能公告（aihot.news 两个相邻条目 id）占了 15 个槽里的 1 个。
  但在当天 616 条在效候选的高分前 40 名里，只有 2 对共享 ≥12 字前缀，另一对是
  `Qwen3.8-Flash 限时免费一周`（公告，93 分）与 `Qwen3.8-Flash 限时免费？`（**提问帖**）——
  前缀 18 字却完全不是同一件事。任何"前缀够长就算重复"的规则都会把后者这类"同名不同事"合并掉，
  而价格差一个数字的条目（`首年 99 元` / `首年 199 元`）差异恰恰在尾部。
  代价 1/15 槽，收益不抵误伤，不做。

- **「近似标题折叠会让新一期公告被过期的占位行吞掉」**（2026-09-21 拿生产库量过，**不成立**）：
  折叠规则确实是"先见者拥有标题"，所以理论上存在一个失败模式——同名不同期的公告（如每月同名的消费券）
  里，新那期被挂到已过期老实例的 `dup_of` 上，于是 `Live` 两边都丢、日报和提醒同时看不见它。
  实测 721 条去重记录里 24 组同名多条，全部是正当折叠（v2ex 的 `#replyN` 锚点、`tencent.com` 与
  `tencent.com.cn` 镜像域、跨源转载），**其中没有任何一行带 `expires_at`**，"后行截止晚于占位行"的组数 = 0。
  所以今天不改：改折叠方向（改成最新者拥有）会动到 `event:reminded:<fp>` 与 `pushed` 的归属，代价大于收益。
  复判办法：在生产库上按 `model.DedupKey` 归组，只看那些**组内出现两个以上不同 `expires_at`** 的组——
  有这种组才说明吞掉了有效公告；一条命令即可数出来，别凭规则的形状下结论。

- **「官方目录差分：推理云 / 向量库 / GPU 云」**（2026-09-21 从生产出口实测后否决）：
  OpenAI 兼容的 `/v1/models` 全部要密钥 —— `api.deepseek.com` `api.moonshot.cn` `api.groq.com`
  `api.together.xyz` `api.siliconflow.cn/v1/models` 一律 401，`api.siliconflow.cn/v1/model/list/all`
  404，`api.github.com/models` 404；只有 `openrouter.ai/api/v1/models` 是公开 JSON（200 / 738KB /
  446 个 id / 带 `prompt`、`completion` 每 token 价格），而它已经在采集。**公开目录这条路没有第二个入口。**
  定价页方向同样不通：`siliconflow.cn/pricing`、`bigmodel.cn/pricing`、`autodl.com/pricing`、
  `cloud.zilliz.com.cn/pricing`、`volcengine.com/product/vikingdb` 全部 200，但页面里
  **服务端渲染的价格标记 `¥<数字>` 命中数为 0**，其中三个只有 3–6 KB 的 JS 壳。要读它们得上无头浏览器，
  而本项目是零第三方依赖的单二进制、不跑浏览器，用户的夜间调度也明确要求不拉起可见窗口。
  结论：这类信息只能靠现有的 `search` 采集器从第三方转述里拿（已在跑），或者等官方给出无需鉴权的目录接口。

## Known Risks

- **投递扇出任一成功即算送达**：一天只有一份消息，所以某个通道坏了当天这份就只存在于日志里。
  目前靠 `notify: partially delivered` 警告与 `/api/v1/status` 暴露，不做重试。真需要更强保证时要先定策略（去重 vs 漏投）。
- **备份目前与生产同盘**：`/var/backups/deal-hunter` 在 `alienware-life` 自己的磁盘上，能救误删与
  状态损坏，救不了整机故障。跨机那份要设 `DH_BACKUP_PUSH`，目标机器由用户定（见 STATUS Notes）。
- **同一场赞助活动换措辞重发，会各提醒一次**：事件通道按 `fingerprint` 去重，而近似标题折叠只认
  `DedupKey`（去标点后相同）。2026-09-21 生产里就有实例：两条 `[推广] 《我享云》机场代理…` 分属
  v2ex `t/1243236` 与 `t/1243515`，措辞差在"比矿泉水还便宜"与"一瓶矿泉水/月"，同一截止时刻
  `09-30 23:59`，两行都进了跟踪列表。每天只有 2 条事件预算，重复一条就占掉一半。
  **不做模糊匹配**：两家不同机场的促销也可能只差几个字，误合的代价是漏提醒。要收敛得先有
  "同一活动"的可靠判据（赞助商 + 时刻 + 领取入口），目前没有。
- **`max_age_hours` 只管入库不管在效**：`filter.max_age_hours`（默认 14 天）只在采集时丢弃
  发布已久的行，且要求 `published_at` 已知；`Store.Live` 没有年龄上限。所以一条**没有**写明截止的
  在效条目会一直留在日报里 —— 这是 `reparse` 存在的原因之一，也是解析器读不出截止的真实代价。
- **日报只在采集轮结束后检查**：`daily.at` 到点后最多再等一个 `interval`（默认 30m）才发；发送失败下一轮重试。

- **插队门槛 90 分只有一个真实样本**：2026-09-21 14:19 `Qwen3.8-Flash 限时免费一周` 打出 93 分并
  真实投出（见 STATUS 第 4 条），落在预测的 87–97 带内。但一个样本不足以判断"门槛是不是太高/太低"，
  也没验证过同一天第二条高分被 `held` 的行为。**别再把它当未验证的估值，也别当已定案的阈值。**
- **排程压缩曾经数的是进程内轮次（已修，M19）**：`scheduler` 每 48 轮触发一次 `Compact`，而轮次是
  **进程内计数**——30 分钟一轮意味着要"连续 24 小时不重启"才凑得满，任何一次部署都把它清零。
  2026-09-21 生产跑了一整天、部署六次，`maint:last_compact` 这个键**至今不存在**。
  当晚手动跑过一次 `compact` 以验证新路径：`deals.jsonl` 1115 → 749 行（`749 → 749 条`，一行没丢）。
  2026-09-22 改成**每轮都检查、以盘上的 `maint:last_compact` 节流（≥7 天才真剪）**，
  重启不再影响触发；`scheduler_test.go` 四条守卫逐个变异复查过（去掉节流 / 去掉首轮检查 /
  剪完不写记号 / 记号读不出当作刚剪过，各红对应那条）。
  剩下的运维问题只有一个：**7 天与 60 天这两个数合不合适**（现在生产 868 行 / 1.4 MB，
  一夜 +119 行，按这个速度 7 天一剪足够稳）。
  **注意这条改动的后果**：排程从此真的会自己删数据（60 天前且分数<60 或已推送的行），
  不再需要额外那条 systemd timer（本条到此作废：不必再加外部定时器，服务自己就会做）。
  生产第一次自动剪枝的时刻 = 盘上记号满 7 天，具体日期记在 STATUS；前一晚有夜间备份兜底。
- **状态键的剪枝要等持有它的进程重启才生效**（写这条是因为我先说过头过一次）：`state.json` 由每个
  打开它的进程整份读进内存、再整份写回。所以常驻服务活着时，`compact` 删掉的键会被它下一次写**任何**
  状态时原样带回磁盘 —— 2026-09-21 我写"退役的 `digest:*` 已被清掉"，第二天它就在生产回来了。
  现在两道一起解决：装载时丢掉退役命名空间（`retiredStatePrefixes`，`digest:` 没有任何读者），
  以及 `PutState` 以磁盘为底合并。剩下的含义要写清楚：**剪枝在下一次重启后彻底生效**，别当即时清理。
- **`Compact` 顺带删掉跟随行而死的缓存键**：`official:deal:<fp>` 只在读的时候判 7 天 TTL，
  键本身从不删；行被压缩掉之后那个键再没人读得到，而 `state.json` 每次写入都是整体重写。
  现在压缩会把"所属行已经不在了"的判定键一起删掉（生效时机见上一条）；
  `official:verify:<url>` 跨行共享，保留。

- **升级后旧配置里的废弃键不报错也不生效**（`notify.digest`、`notify.feishu.{min_score,max_per_run,silent_hours}`、`filter.min_score`），`install.sh` 会打一行提示。

## Technical Debt
- **`Store.Live` 每次都整体重读 JSONL —— 量过，不是债**：2026-09-21 生产实测 `daily -dry`
  端到端 `0.09 s`（含进程启动、配置、整库解码、渲染），而真实采集轮次是 `2.8–6.0 s`（17 个源的
  网络耗时占大头）。库 1.2 MB / 779 行。就算长到 10 倍也只是每次多几百毫秒，且轮次本来就是网络瓶颈。
  **别为此加缓存**——那会引入"缓存与追加写不一致"这类新故障，而现在的成本是零。
- `internal/scheduler` 没有测试文件：`Loop` 直接依赖 `*pipeline.App`，要测触发逻辑得先抽一个小接口（**故意没做**，避免为测试造抽象）。
- 采集器类型有 7 种，`sources.New` 是一个 switch；再加两类以上时值得回到注册表写法。

## Non-Goals

- 不引入数据库、Docker、消息队列、微服务拆分或前端构建链（JSONL + 单二进制是特性不是债）。
- 不跑无头浏览器去读 SPA 定价页：那等于把"零第三方依赖"换成一个 Chrome。这类信息拿不到就是拿不到，
  宁缺毋滥（实测见「已实测否决的方向」）。
- 不用 GitHub Actions 当门禁（额度优先留给代码托管与 Release）。
- 不做多群路由 / 分类订阅：目前只有一个读者。
- 不把 `0.0.0.0` 暴露成公网服务，也不为公网访问写认证层。
