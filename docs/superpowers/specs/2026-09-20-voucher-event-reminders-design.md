# 设计：本地消费券采集与开抢前提醒

日期：2026-09-20 · 状态：待用户复核 · 里程碑：M3
前置：M2 已把交付形态收敛为「一天一份日报 + 高分当天最多插队一次」（`80721b3`）

## 1. 问题

用户常驻**江西南昌**，想让 Deal-Hunter 盯本市发放的消费券，并在**开抢前**提醒。
这类信息与现有内容的根本差别是：**它是一个有时刻的事件，不是一项可以一直领的额度。**

现有链路对此没有准备：

- 调度只有两种触发 —— 采集轮结束时的分数突破检查、每日固定时段的日报。没有「未来某时刻触发」这一类。
- `Store.Live()` 判定「仍在效」的规则是「没有 `expires_at` = 仍然有效」。这对 openrouter 免费模型成立，
  对消费券**必然误判**：实测调研与样本都表明政府公告永不下架也不标结束
  （甘肃高台 6 月端午券公告在 9 月仍挂在栏目列表里）。若直接接入，9 月的日报会宣布 6 月的券「持续在效」。
- `html` 采集器只抓配置的那一页，不跟进链接（`internal/sources/html.go:59` 的 `PublishedAt` 恒为零值），
  而开抢时间写在公告**正文**里，且常常不标年份、要靠页面发布日推断。

## 2. 目标与非目标

**目标**

1. 从南昌本市官方栏目发现新公告，识别其中的**开抢时刻**与**有效期**。
2. 在开抢前一个可配窗口内**恰好提醒一次**，跨重启不重复。
3. 修正「仍在效」判定，使**限时事件类**条目不再因缺少期限而赖在日报里。

**非目标**（明确不做，各有理由）

- 不做端内核验：云闪付 / 支付宝 / 美团 / 建行生活的活动页是端内 H5，需登录与签名，普通 GET 拿不到额度与剩余量。
  采集到的公告会如实标注「额度与剩余需自行在平台确认」。
- 不解析 PDF / 长图附件里的每日额度表：会破坏零第三方依赖这一核心特性。
- 不做「每个信息源独立抓取间隔」：提醒精度改为绑定全局采集间隔（见 §6 取舍），先不做更复杂的调度。
- 不做栏目改名 / 迁站导致的「源静默 0 命中」检测与告警：列为技术债，不在本里程碑发明健康度机制。
- 不识别「每日 9 时定量投放」这类重复轮次（兴城式表述）：文本上歧义过大，先按「解析不出明确日期+时刻就不当事件」处理。

## 3. 交付形态：第三类消息

| 消息 | 触发 | 每日上限 |
|---|---|---|
| 🌅 日报 | 每日固定时段 | 1 |
| ⚡ 高分突破 | 单条分数 ≥ 90 | 1 |
| ⏰ **事件提醒**（新增） | 某条目的 `starts_at` 落入提醒窗口 | 2（每事件至多 1 次） |

消费券**不进**日报的「在效」集合，除非公告本身写明了有效期（见 §7）。

## 4. 数据模型

- 新增 `model.CatVoucher`（类别：本地消费券 / 限时抢购事件）。
- 新增 meta 键 `starts_at`（RFC3339，UTC 存储），与既有 `expires_at` 对称。
- `internal/keywords` 新增 `StartsAt(text string, anchor time.Time) *time.Time`，与现有
  `ExpiresAt`（`internal/keywords/keywords.go:240`）并列，共用其日期归一设施。
  必须覆盖调研实测到的写法：`2026年6月18日上午9时开始发放`、`8月24日中午12:00`、
  `9时 / 9：00 / 上午9点 / 10:00` 四种并存，含上午/中午/晚上的 24 小时换算；以及
  **只有月日无年份**时借 `anchor`（页面发布日或条目 `PublishedAt`）推断。
- **不解析重复轮次**：`每日上午9:00发放` 这类表述**单独出现时不产生 `starts_at`** —— 它与
  「首日 9:00 开一次」在文本上无法区分（调研中興城公告两种读法都成立）。只有当同一段文本里
  另有明确日期（或明确活动起止区间）时，才允许把那个时刻与日期组合成 `starts_at`。
  这与 §2 非目标里"不识别每日定量轮次"是同一条规则的两种说法，不是矛盾。
- **不可猜**：解析不出「明确日期 + 明确时刻」就不写 `starts_at`。宁可漏一条提醒，
  也不能发一条猜出来的提醒 —— 后者会让用户对整个通道失去信任。
- 新增 `Deal.IsDatedEvent() bool`：`Category == CatVoucher` 或 `starts_at` 存在。
  §7 的口径分叉就以它为唯一判据，不新增更多分类概念。

## 5. 采集

### 已验证的南昌信源

全部在 2026-09-20 从**生产机出口**（`alienware-life`）以无 Cookie、无登录、自定义 UA 的普通
HTTP GET 实测；编码均为 UTF-8，正文均服务端渲染，因此现有 `html` 采集器可直接工作。

| 信源 | URL | 实测 |
|---|---|---|
| 南昌市商务局 · 通知公告 | `https://swj.nc.gov.cn/ncsswj/tzgg/index.shtml` | 200，98 KB，含唯一条目与 `<i class="time">` 日期，标题含「消费券」 |
| 南昌市人民政府 · 通知公告列表 | `https://www.nc.gov.cn/ncszf/tzgg/2021_nav_list.shtml` | 200，32 KB，15 条唯一条目，16 个日期串 |
| 详情正文（二跳目标示例） | `https://swj.nc.gov.cn/ncsswj/tzgg/202609/442d376f664948a38e4c2e61a696ff68.shtml` | 200，11 KB，UTF-8，正文含「消费券」4 次 |

两条必须记住的坑（均已实测）：

1. `https://www.nc.gov.cn/ncszf/tzgg/` **307 跳回首页**。配成源会静默失败：拿到首页 HTML、
   解析出一堆无关条目、永远命中不到券。**必须配具体列表页**。
2. 栏目名里的年份（`2021_nav_list`）是 CMS 遗留，内容与 2021 无关 —— 不要据此判断源已过期。

区县栏目（东湖 / 西湖 / 青山湖 / 红谷滩等）与商务局「公告公示」子栏目
（`gkgsgg/bmxxgk_list_2.shtml` 实测返回 307，已弃）**在实施阶段按 §「信源准入」流程逐条实测后再加**：
先用生产机出口确认可达 + 编码 + 列表结构 + 标题含券样本，四项齐了才写进配置。
未通过实测的 URL 一律不进默认配置。

### 信源准入规则（写进配置，也用于后续加源）

```
kind: html
keywords: [消费券, 惠民券, 抢券, 核销, 领取]
deny_keywords: [以旧换新, 汽车置换, 家电补贴, 招标, 中标, 候选人, 遴选, 服务机构]
follow_detail: true
detail_min_text_len: 200
```

关键词表刻意不放「满减」：`keywords` 是子串匹配，`满 减` 这种带占位的写法永远命中不了，
而满减折扣已由现有词典与评分项处理，不需要在这里重复。
`detail_min_text_len: 200` 是初值，不是测出来的数：真实公告正文实测为 427 字（徐汇）到
数千字，200 只用于挡下频控页与错误页，跑起来后按实际噪声调整。

- **关键词门在列表页上执行**，只有通过门的那几条（实测首页 20 条里 0–1 条）才触发详情二跳，
  所以每轮额外外连是 0–2 次，不是 20 次。
- `deny_keywords` 的存在理由经实测确认：商务局栏目里大量条目是「发放服务机构遴选 / 名单公示」，
  即"谁来发"而非"几点开抢"；它是**有价值的预告**，但不是事件，不能当成可领的券。
- 列表行里的 `YYYY-MM-DD` 解析为 `PublishedAt`，作为无年份日期的推断锚点。
- **200 不等于成功**：详情正文长度低于 `detail_min_text_len` 或不含「发放 / 核销 / 领」任一词，
  视为无效抓取，不写 `starts_at`，条目退回普通路径。这条同时挡掉调研中发现的
  「200 返回频控拦截页」类误判。
- 详情二跳失败不阻塞整轮，计入该源错误（与现有单源错误隔离一致）。
- 新条目检测**不需要新游标**：指纹即 URL 哈希，`Store.Seen()` 已处理重复；列表页 15–20 条滚动窗口
  远大于日发文量，30 分钟轮询不会把新条目挤出。

### 新增采集能力

`html` 采集器加一个默认关闭的参数 `follow_detail`：对每条通过关键词门的条目，GET 其链接一次，
用正文（而非列表行）做后续解析与评分。默认关，因此对现有 15 个源零影响。

## 6. 调度

```
notify.event = { enabled: true, lead_time: 45m, late_grace: 15m, max_per_day: 2, min_score: 60 }
```

`event.min_score` 是**成为事件的地板**（默认 60）：低于它的条目即便解析出了 `starts_at` 也只当普通
条目，不配打断读者 —— 挡的是《如何领取养老服务消费券》这类低分 how-to。它与 §7 的日报口径无关，
也不复用 `urgent.min_score`（那是"值不值得插队"，这是"算不算一个事件"）。

判据（在采集轮结束时评估，沿用 M2 的结构，**不引入独立定时器**）：

> **候选集是库，不是本轮新入库的条目。** 公告通常在开抢前几天发布，本轮扫到的条目此刻
> 往往还没进窗口；只扫本轮结果会让所有提前发布的事件永远等不到提醒。实现落为
> `Store.Upcoming(from, through, min)` + 已提醒过滤。

```
应提醒(d, now) =
      d.starts_at 存在
  && d.score >= event.min_score
  && 未曾提醒过该指纹
  && now ∈ [starts_at - lead_time, starts_at + late_grace]
```

- 幂等与重启安全：状态键 `event:reminded:<fingerprint>` 记一次落盘。
- 每日预算：`event:sent` 与 `urgent:sent` 同形状（`{"date":本地日,"n":计数}`），按 `timezone` 的本地日记账。
- **预算耗尽时的语义（明确定死）**：不消耗幂等键，因此窗口内后续采集轮仍会尝试；一旦离开窗口
  （超过 `starts_at + late_grace`）即放弃该事件的提醒，但条目仍在库里，若它写明了有效期，
  照常出现在日报。预算与幂等是两件事，不能混。
- 投递失败同样不记提醒、不记预算，下一轮重试（与 M2 突破通道一致）。
- 预算耗尽时**不静默丢弃**：记 `Run.EventHeld`，面板与 `/api/v1/status.event` 可见。
- `starts_at` 一律按配置 `timezone` 解释后转 UTC 存储；服务常年跑 UTC，
  否则「10:00 开抢」会被推成 18:00。此路径必须有测试。

**取舍必须写明白**：提醒时刻精度 = 全局采集间隔。默认 30m 下，10:00 开抢的券被发现于
09:35（提前 25 分，够用）或 10:05（靠 15 分钟宽限救回）。`lead_time` 取 45m 而非 30m 正是为此。
要分钟级 precision 需引入单源间隔，已在非目标里排除。

## 7. 日报口径修正

`Store.Live()` 的「仍在效」判定按类别分叉，不加全局 TTL 数字：

- **长期额度类**（现状不变）：无 `expires_at` → 视为仍然有效。
- **限时事件类**（`IsDatedEvent()`）：**必须**有 `expires_at` 且未过期才进日报；缺失即视为已失效。

三种真实情形因此正确：写明「核销期限 7 天」的券能进日报；「活动期 5/1–5/5 每日 9 时」的券
5/6 起自动出局；什么都没写的公告只在开抢前播一次。
已知代价（接受）：确实长期有效但正文含糊、不写期限的券会被日报漏掉 —— 方向上漏报优于
「9 月推 6 月的券」这种把读者信任耗光的误报。

## 8. 投递

`notify.KindEvent`，卡片抬头：`⏰ 今天 10:00 开抢 · 南昌市 XX 消费券`，
正文一行一条（复用现有 `dealLine`），附「额度与剩余请在平台确认」。
事件消息必须在**三条渲染路径**上都带上「开抢时刻」与（若有）「有效期」：飞书卡片、
`Message.Plain()`（控制台与文件投递）、OpenClaw 中转文本。M2 的教训是 relay 会把日报分段压平，
这次用同一个 `Plain()` 渲染函数出口，避免再出现"某条通道丢了字段"。

## 12. 已知风险

- **信噪比**：实测商务局首页 20 条里仅 1 条含「消费券」，且是《如何领取养老服务消费券》这类
  how-to，不是新券。因此关键词门必须配 `deny_keywords`，且事件判定严格要求解析出时刻。
- **标题含「消费券」≠ 新券发放**：机构遴选公示会提前数周出现，是预告不是事件。
- **提醒精度受全局间隔约束**：用户若要求分钟级 precision，需回来补「单源间隔」设计。
- **公告不标结束**：券的实际投放可能提前结束（"领完即止"），我们无法从网页得知。
- **CMS 迁站/栏目改名**会使源静默 0 命中（列为技术债，见 ROADMAP）。
- **PDF / 长图细则**：每日额度表常在附件里，纯文本抽取拿不到。

## 13. 实施记录（写代码时发现的、设计阶段没看到的）

- **§6 的候选集漏洞**：设计只写了判据没写"从哪个集合里找"，若按字面实现成本轮条目，
  提前几天发布的公告将永远等不到提醒。已改为扫库（`Store.Upcoming`），见 §6 的补充。
- **`ExpiresAt` 既存缺陷两处，均已修**：① `time.Date` 把「有效期至2026年9月31日」进位成
  10 月 1 日，读不懂的截止日变成更晚的截止日；② 「核销期限 / 使用期限」不在前置词表里，
  而这正是消费券公告表述截止的常用写法 —— 不补，§7 会把所有券挡在日报之外。
- **多条事件的时刻**：抬头只放得下一个时间，所以 `len>1` 时每条在自己的行上带时刻
  （`· 09月21日 10:00 开抢 · 标题`），否则读者只知道"有两场要开抢"。
- **时区缺陷已修（同日，M3 之后）**：`ExpiresAt` 原先用 `time.Local` 构造时刻，而比较用绝对时间 ——
  服务跑 UTC 时北京的截止日多活约 8 小时。现在与 `starts_at` 同规矩：截止日也按调用方给出的
  读者时区（`scoring.Input.ReaderZone`，原 `StartsIn` 改名，因为它的含义已覆盖两端）构造。
  两道守卫都写成"两个时区必须差出整 8 小时"，因此不依赖测试主机自身时区；分别把
  `keywords` 与 `scoring` 的传参改回旧写法都验证过会变红。
- **仍未验证**：真实"开抢前收到一次提醒"要等南昌下一条带明确时刻的公告。
